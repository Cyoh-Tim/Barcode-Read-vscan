1부 — 코드를 직접 뜯어본다

1.1 이 물건이 무엇인가

한 줄: 카메라가 찍은 흑백 사진 한 장을 받아서, 그 안에 있는 바코드를 전부 찾아 읽고, 읽은 문자열과 위치를 돌려주는 C++ 라이브러리다.

돌아가는 곳: i.MX8M Plus라는 산업용 보드. ARM 코어 4개, 우리가 개발에 쓰는 x86 PC보다 약 8배 느리다. 이 8배는 이 저장소 전체에서 계속 나오는 숫자라 기억해 두면 좋다 — 문서의 모든 시간은 x86 실측이고, 보드 값은 ×8이다.

바탕: zxing-cpp라는 오픈소스 바코드 라이브러리를 감싼다. 다만 "감싼다"가 얇은 래퍼라는 뜻은 아니다. zxing-cpp에 그냥 사진을 주면 실패한다 — 이 저장소의 코드 13,570줄 중 대부분은 "zxing이 읽을 수 있는 상태로 사진을 만들어 주는" 일과 "여러 번 시도하되 시간 안에 끝내는" 일이다.

사진 (2048x1536 회색조)
   │
   ├─ [우리 코드] 조건을 재고, 고치고, 자르고, 돌리고, 확대하고…
   │
   └─→ zxing-cpp ─→ "VSCAN-SWEEP-01" + 네 꼭짓점 좌표

1.3 프레임 한 장이 지나가는 길

핵심 함수는 Pipeline::processView() (src/pipeline.cpp:558)다. 단계 이름은 VSPROF=1 환경변수를 주면 실제로 찍힌다:

[prof] 성공:denoise 합계 787.3ms | ts:coarse=1.2 ts:fast=8.2 rg:crop=15.4
       rg:persp=1.3 rg:pitch=0.1 rg:invert=14.3 rg:contrast=232.4
       ts:region=275.3 ts:harder=37.2 ts:invert=41.2 pre=0.4 core=76.3
       tilefb=71.6 dn:filter=12.5

순서는 이렇다. 위에서 성공하면 아래는 안 돈다 — 그게 이 구조의 전부다.

 0. frameHasStructure()   빈 프레임이면 즉시 끝    (컨베이어 공백: 36ms → 0.1ms)
 1. pre                   전처리 — 조건을 재고 필요할 때만 고친다
 2. core                  타일로 쪼개 병렬 디코드   ← 대부분 여기서 끝난다
 3. tilefb                타일보다 큰 코드용 전체 스캔
 4. dn:filter/decode      뭉개서 다시 (노이즈 구제)
 5. ff:filter/decode      조명 평탄화 후 다시 (그림자 구제)
 6. dpm                   도트 각인 구제
 7. rg:*                  영역 구제 — 후보 영역을 잘라서 확대/회전/원근/곡면
 8. qrfinder              QR 파인더 패턴으로 직접 찾기 (기본 꺼짐)
 9. deskew1d              1D 기울기 보정

왜 사다리인가

단순히 "다 해보면 되지 않나"가 안 되는 이유는 시간이다. 산업 현장은 컨베이어가 돌고 있고, 프레임 하나에 쓸 수 있는 시간이 정해져 있다. 그런데 위 단계를 전부 돌면 x86에서 800ms, 보드에서 6.4초다.

그래서 구조가 이렇다:

  • 쉬운 프레임은 2단계에서 끝난다 (x86 5~20ms)
  • 어려운 프레임만 사다리를 내려간다
  • 마감(max_frame_ms)을 걸면 중간에 끊는다

실측으로 보면 이 분포가 극단적이다. 300장 코퍼스에서 중앙값(p50)은 5ms인데 p95는 300ms다. 60배 차이다. 평균만 보면 이 구조를 이해할 수 없다.

단계 하나를 예로 — core

std::vector<PipelineResult> Pipeline::processViewCore(const GrayView& image,
                                                      bool tileFallback) {
    // 프레임을 가로로 잘라 타일 N개로 나누고 스레드 N개로 병렬 디코드
    // 타일 사이에 tileOverlapPx(기본 500px) 겹침을 둔다

겹침이 500px인 이유가 재밌다. 겹침이 코드 세로 크기보다 작으면 코드가 타일 경계에서 잘려서 어느 타일에서도 안 읽힌다. 실기 차트의 QR이 세로 460~600px이라 500px + 여유로 정했다.

그런데 겹침을 크게 두면 같은 코드가 두 타일에서 각각 읽혀 중복이 된다. 그래서 dedup()이 필요해졌고, dedup이 지금 이 코드베이스에서 가장 규칙이 많은 함수 중 하나가 됐다(아래 1.6).

1.4 전처리 — "조건을 먼저 재고, 맞는 것만 한다"

preprocessFrame() (src/pipeline.cpp:666 부근)은 이 프로젝트의 설계 철학이 가장 잘 드러나는 자리다. 초기 버전은 이랬다:

[낡은 방식] 모든 프레임에 디노이즈 + 평탄화 + 이진화를 다 건다

이러면 깨끗한 프레임까지 비용을 낸다. 그래서 커밋 338bb0d(수렴 전략 S1~S4)에서 뒤집었다:

const float noise = estimateNoise(image);      // 먼저 잰다
if (noise > threshold) {                        // 필요할 때만
    boxBlur3x3(image, denoiseBuf_);
    preDenoised_ = true;
}

결과: 최악 프레임과 최선 프레임의 시간 차이가 69배 → 2.8배로 줄었다.

이진화 — 이 저장소가 zxing을 못 믿는 첫 자리

바코드 디코딩은 결국 "이 픽셀이 검정인가 흰색인가"로 시작한다. 그런데 조명이 고르지 않으면 전역 임계값 하나로는 안 된다.

preprocess.cpp에는 임계 방식이 여러 개 있고, 실측으로 고른 순서가 있다:

방식언제 이기나
전역 히스토그램깨끗하고 균일한 조명
블록 적응조명 기울기
행 단위 적응대비 0.05 같은 극저대비 ← 커밋 8354a18
세로 평균 선행1D에서 세로 방향 노이즈

커밋 8354a18의 제목이 "대비 축 100%: 임계를 블록이 아니라 행 단위로 잡는다"다. 1D 바코드는 세로로 같은 무늬가 반복되므로, 행 하나 안에서 임계를 잡으면 조명 기울기를 자동으로 상쇄한다. 블록 단위로는 블록 경계에서 임계가 튀어서 바가 끊긴다.

1.5 코드를 어떻게 찾는가 — 로케이터

findCodeRegions() (src/locate.cpp)의 원리는 단순하다:

  1. 이미지를 4배 축소한다 (빠르게 하려고)
  2. 32×32 타일로 나눈다
  3. 각 타일의 기울기 에너지(gradient energy)를 잰다
  4. 프레임 최대 에너지의 20% 이상인 타일만 남긴다
  5. 남은 타일을 이어 붙여 영역으로 만든다

바코드는 흑백 경계가 촘촘해서 기울기 에너지가 높다. 배경(종이, 벽)은 낮다. 그래서 잘 동작한다 — 노이즈가 없으면.

여기서 이번 세션에 찾은 결함 (§3.108)

4번의 "프레임 최대 에너지의 20%"가 상대 기준인 것이 문제다. 센서 노이즈가 얹히면 배경 타일의 에너지가 통째로 올라가서 거의 모든 타일이 임계를 넘는다. 그러면 영역이 하나로 뭉쳐 프레임 전체 상자가 나온다.

실측 — 같은 코드, 크기도 같고, 노이즈만 다르다:

영역 크기
DataMatrix 60×60, 노이즈 0256×256 (정확)
DataMatrix 60×60, 노이즈 252048×1536 (프레임 전체)

프레임 전체 상자를 크롭해 봐야 원본과 같으니 아무것도 못 번다. 그래서 "코드를 못 찾는다"가 아니라 "찾았다고 하는데 쓸모가 없다"는 형태로 실패한다.

고친 방식: 결과가 이미 쓸모없을 때만(영역이 프레임의 55% 초과) 임계를 0.65로 올려 다시 찾는다. 처음부터 올리면 코드가 여럿인 프레임에서 약한 코드가 강한 코드에 밀려 후보에서 빠진다.

되살리는 로케이트는 타일 16 / 축소 2로 돈다. 임계만 올리면 상자가 타일 격자만큼 헐렁해서(60×60 코드가 256×256 상자) 그 크롭이 다시 실패하기 때문이다:

크롭 크기결과
256×256미검출
192×192읽음
96×96읽음

노이즈 프레임에서는 코드 밖 면적이 곧 오검출 기회다.

1.6 중복 제거 — 규칙이 여섯 개인 이유

같은 코드가 여러 번 나오는 경로가 많다:

  • 타일 겹침에서 두 번
  • 원본과 구제본에서 각각
  • zxing과 ZBar 둘 다 붙였을 때

그래서 dedup()이 필요한데, "같은 텍스트면 하나로" 만으로는 안 된다. 박스에 같은 라벨이 두 장 붙어 있는 배치가 실제로 있기 때문이다. 그건 진짜 코드 두 개다.

지금 있는 규칙들:

규칙무엇을 잡나
dedup-degenerate-quad꼭짓점이 겹쳐 위치를 못 믿는 결과
dedup-partial-scan한쪽 텍스트가 다른 쪽의 부분 문자열 (ITF 20/70도)
dedup-thin-slice두께가 상대의 35% 미만인 스캔 조각
dedup-stacked-band세로로 붙은 밴드
dedup-twin-band같은 코드를 위아래로 스친 두 밴드
dedup-single-band자기 길이의 15% 이하 두께 = 스캔 밴드

각 규칙에는 양성 대조가 붙어 있다. tools/generate_stacked_labels.py가 같은 라벨 2장을 간격을 바꿔가며 만들고, 게이트가 "간격 240px면 둘 다 나와야 한다"를 지킨다. 규칙을 세게 만들면 이 대조가 먼저 깨진다.

1.7 이번 세션에 추가된 것 — 저해상도 1D 강등

풀테스트에서 오디코딩(없는 코드를 만들어내는 것) 88건을 한 건씩 재생성해 확인했더니 이런 게 나왔다:

ITF '681731'   ← 정답 '867935681731' 의 뒤 6자리
ITF '31803327' ← 정답 '7631803327'   의 뒤 8자리

처음 진단은 틀렸다. "바 열을 끝까지 못 훑은 부분 스캔"이라고 보고 정지대(quiet zone) 검사를 넣었는데 87건 중 3건만 걸렸다.

한 장을 계측해서 전제를 다시 쟀다:

[qz] quad (500,159) (406,159) (405,161) (499,161)   L=94
[qz] 관측 요소 36개                    ← 6자리 ITF의 기대값이 37개
[qz] side-1 전이=1   side+1 전이=0     ← 양쪽 다 정지대다

세 가지가 한꺼번에 전제를 무너뜨렸다. 상자가 코드 전체를 덮고 있고, 양 끝이 정지대이고, 요소 개수가 6자리와 일관된다. 즉 디코더는 자기가 본 것과 맞는 답을 냈다. 틀린 것은 본 것 자체다.

이 결과는 3배 축소된 뷰에서 나왔고 거기서 좁은 요소가 1.0px이었다. 12자리(요소 67개)가 94px에 들어가면 요소당 1.4px이라 이웃한 좁은 요소들이 뭉개진다. 뭉개진 무늬를 ITF 문법으로 읽으면 원본의 부분 수열이 나온다 — 그래서 결과가 정답의 꼬리처럼 보였던 것이다.

요소 하나를 가르려면 표본이 최소 둘은 있어야 한다(나이퀴스트). 이 저장소가 §3.61에서 따로 찾은 "모듈 2px 벽"과 같은 수다. 두 경로로 같은 수에 도달한 것이 이 진단의 근거다.

그런데 버리면 손해였다:

모드텍스트 일치오디코딩
끔42.23%25
버림41.86%26
프레임 단위 강등41.89%22
코드 단위 강등42.71%23

세 번째와 네 번째의 차이가 내가 짠 규칙의 결함이었다. 강등이란 "이 코드에 더 나은 답이 있으면 물러난다"인데 "프레임 어딘가에 더 나은 답이 있으면 물러난다"로 짰다. 난수 코퍼스는 한 장에 코드가 최대 12개라, 다른 코드를 맞게 읽은 약한 결과까지 같이 버리고 있었다. 245코드를 그렇게 잃고 있었다.

CSV를 통째로 비교하니 바이트 단위로 같았다. 원인은 생성기의 이 세 줄이었다:

span = max((gw + 2 * quiet), (gh + 2 * quiet) if is2d else 0)
if span * mod > box:

폭이 넓은 1D는 이 클램프에 항상 걸려서 요청 4든 8이든 같은 값(3.66px) 으로 포화했다. 진짜 문제는 중복 계산이 아니라 비교가 깨진 것이다 — 같은 "모듈 8" 칸에서 EAN13은 8.00px, CODE39는 3.66px을 받는다. 그 상태로 검출률을 나란히 놓은 표는 심볼로지가 아니라 크기를 비교한다.

그리고 나는 실제로 그 표를 읽고 "CODE128은 블러에 약하다"라고 결론 낼 뻔했다. 라이브러리 문서에 심볼로지 권고로 남을 문장이었다.

고친 방식: 모듈을 깎지 말고 캔버스를 넓힌다. 코드와 프레임의 비율이 그대로라 "모듈당 표본 수"라는 축만 혼자 움직인다. 상한(12MP)에 걸리면 예전처럼 깎이지만, 그때는 태그에 실제 모듈이 찍힌다:

angle=0,module=8,sym-CODE_93,modpx-6.27,img-ok
                             ^^^^^^^^^^ 요청 8인데 6.27을 받았다
규칙: 요청값과 실제값이 다를 수 있으면, 실제값을 산출물에 적을 것. 생성기가 물리적 제약 때문에 요청을 못 지키는 것 자체는 정상이다. 문제는 그 사실이 결과물 어디에도 안 남는 것이다.

왜 모듈 격자로 정규화하나

인코더마다 출력이 제각각이다(비트열/PIL 이미지/행렬). 이미지를 그냥 리사이즈하면 모듈 폭 비율이 깨진다. 그래서 전부 모듈 격자로 되돌린 다음 우리가 원하는 크기로 다시 그린다.

되돌리는 방법이 재밌다 — 최소 런 길이 = 모듈 하나의 픽셀 크기라는 성질을 쓴다:

u = max(1, min(min_run(a), min_run(a.T)))     # 모듈은 정사각이라고 본다
h = max(1, int(round(a.shape[0] / u)))
w = max(1, int(round(a.shape[1] / u)))

센서 노이즈 바닥 (§3.102)

이 코퍼스에는 오래 노이즈가 아예 없었다. noise가 축으로만 있고 기본값이 0이었다. 그런데 실제 카메라는 노이즈가 0인 적이 없다.

def sensor_noise_floor(arr, rng, extra_sigma=0.0):
    read = 2.2                                    # 읽기 노이즈
    shot = np.sqrt(np.maximum(arr, 0.0)) * 0.16   # 광자 산탄 노이즈
    sigma = np.sqrt(read ** 2 + shot ** 2 + float(extra_sigma) ** 2)
    return arr + rng.normal(0, 1, size=arr.shape) * sigma

이걸 넣으면서 검출률이 0.7%p 떨어졌다. 그 0.7%p는 잃은 성능이 아니라 과대평가였던 부분이다.

규칙: "항상 있는 것"을 옵션으로 두지 말 것. 렌즈 MTF 블러는 이미 항상 걸고 있었는데 센서 노이즈만 축이었다. 둘 다 물리적으로 항상 있는 것이라 같은 대우를 받아야 한다.

판독 가능성 버킷 — 그리고 이번에 고친 것

classify_code()가 코드 하나를 ok / borderline / impossible로 나눈다. "물리적으로 읽을 수 있는가"를 판정하는 것이라, 성능 주장은 ok 행에서만 해야 한다.

그런데 이 분류기가 손상과 오염을 아예 안 보고 있었다. 90%가 지워진 QR도 img-ok였다. 생성기 주석에 그렇게 적혀 있었는데 ([[vscan-lite-sweep-damage-uncalibrated]]), 내가 풀테스트 보고서를 쓰면서 그 경고를 어기고 F격자 절대값을 성능처럼 실었다 — QR 14.7%가 그것이다.

고친 방식: 파괴량을 모델링하지 않고 잰다. 손상을 그리기 전후를 빼면 정확한 값이 나온다:

before = np.array(sym, dtype=np.int16)
after  = np.array(im2, dtype=np.int16)
code_px = before < 128                          # 원래 검정이던 모듈
killed  = code_px & (np.abs(after - before) > 64)
dmg["frac"] = float(killed.sum()) / max(1, int(code_px.sum()))
damaged 0.25 → 파괴 3.4%    0.50 → 11.7%
damaged 0.75 → 24.4%        1.00 → 33.6%

그 값을 오류정정 용량과 견준다 — QR은 L 7% / M 15% / Q 25% / H 30%, DataMatrix ECC200 28%, PDF417 18%.

1D는 오류정정이 없는 대신 세로 여유가 있다. 스캔 라인 한 줄만 성하면 읽히므로, 면적이 아니라 "깨끗한 행이 남아있는가"로 판정한다. 물리가 다르니 판정도 달라야 한다.

1.14 이 저장소의 작업 규칙

  2. 측정하고 나서 말할 것. 가설은 절반이 틀린다.
  3. 안 되는 것 목록은 빨리 썩는다. 전제가 바뀌면 다시 재라.

  1. 요청값과 실제값이 다를 수 있으면 실제값을 남길 것.
  2. 규칙이 거의 안 걸리면 문턱이 아니라 전제를 의심하라.

2부 — 열두 살에게 설명한다면

여기서부터는 어려운 말을 하나도 안 쓴다. 1부를 안 읽어도 된다.

2.1 바코드가 뭐냐면

과자 봉지 뒤에 있는 검은 줄무늬. 계산대에서 "삑" 하는 그거다.

그 줄무늬는 사실 숫자를 그림으로 바꿔 놓은 것이다. 굵은 줄, 얇은 줄, 굵은 흰칸, 얇은 흰칸… 이걸 순서대로 읽으면 숫자가 나온다.

모스 부호랑 똑같다. 점과 선으로 글자를 적는 것처럼, 굵기로 숫자를 적는다.

정사각형 모양(QR코드)도 있다. 이건 줄이 아니라 바둑판처럼 생겼고, 훨씬 많은 정보를 담을 수 있다.

2.2 우리가 만든 건 뭐냐면

사진을 보고 그 줄무늬를 읽어주는 프로그램이다.

공장에서 쓴다. 컨베이어 벨트 위로 상자가 지나가고, 카메라가 사진을 찍고, 우리 프로그램이 "이 상자는 A-12345번이야"라고 알려준다.

2.3 근데 이게 왜 어렵냐면

"사진 보고 줄무늬 읽는 게 뭐가 어려워?"

여기서부터가 진짜 얘기다. 공장 사진은 깨끗하지 않다.

어려움 1 — 너무 작다

멀리서 찍으면 줄무늬가 아주 얇아진다. 얼마나 얇냐면, 줄 하나가 사진에서 점 2개 크기밖에 안 될 때가 있다.

점 2개로 굵은 줄과 얇은 줄을 구분해야 한다. 점 1개가 되면? 그땐 아무도 못 읽는다. 정보가 사라져 버린 거다. 이건 우리 프로그램이 못나서가 아니라 물리적으로 불가능한 거다.

비유: 모래알에 글씨를 쓰고 그걸 사진으로 찍었다고 생각해 보자. 사진이 아무리 좋아도 모래알보다 작은 글씨는 안 보인다.

어려움 2 — 어둡거나 너무 밝다

창고는 어둡다. 어두우면 카메라가 밝기를 억지로 올리는데, 그러면 사진에 모래알 같은 점들(노이즈)이 잔뜩 낀다. TV 채널 안 나올 때 지직거리는 그거다.

반대로 형광등이 반사되면 하얗게 타버려서 줄무늬가 안 보인다.

어려움 3 — 비뚤어져 있다

상자가 반듯하게 놓여 있을 리가 없다. 돌아가 있고, 기울어져 있고, 캔이나 병이면 둥글게 휘어져 있다.

둥근 캔에 붙은 라벨은 가운데는 넓고 양쪽 끝은 좁아 보인다. 그러면 줄 굵기가 위치마다 달라져서, 그냥 읽으면 틀린 숫자가 나온다.

어려움 4 — 더럽고 찢어져 있다

공장이니까 기름때가 묻고, 긁히고, 찢어진다.

어려움 5 — 시간이 없다

컨베이어는 계속 돈다. 한 장에 1초씩 쓰면 안 된다.

어려움 6 — 컴퓨터가 느리다

우리가 쓰는 공장 컴퓨터는 개발용 컴퓨터보다 8배 느리다. 개발 컴퓨터에서 1초 걸리면 공장에선 8초다.

2.4 어떻게 푸느냐 — 계단 내려가기

우리 프로그램은 이렇게 생각한다:

"쉬운 건 빨리, 어려운 건 천천히."

계단이 있다고 생각해 보자. 맨 위 칸이 제일 쉽고 빠르다.

1층: 그냥 읽어본다                      ← 대부분 여기서 끝 (아주 빠름)
2층: 사진을 조각내서 각각 읽어본다
3층: 흐릿하게 만들어서 다시 (모래알 지우기)
4층: 밝기를 고르게 펴서 다시 (그림자 지우기)
5층: 코드가 있을 만한 곳만 오려내서 크게 확대해서 다시
6층: 삐뚤어진 걸 반듯하게 펴서 다시
7층: 휘어진 걸 펴서 다시

한 층에서 읽으면 아래층은 안 간다. 그래서 깨끗한 사진은 눈 깜짝할 사이에 끝나고, 지저분한 사진만 오래 걸린다.

실제로 재보면:

  • 절반의 사진: 5밀리초 (1초의 200분의 1)
  • 제일 어려운 사진: 300밀리초

60배 차이다.

2.5 제일 조심하는 것 — 거짓말

여기가 이 프로젝트에서 제일 중요한 규칙이다.

프로그램이 실수하는 방법은 두 가지다:

(A) "못 읽겠어요" ← 괜찮다. 다시 찍으면 된다.

(B) "A-12345번이에요"라고 했는데 사실은 A-12399번 ← 큰일난다.

왜 큰일이냐면, 공장에서 이러면 엉뚱한 물건이 엉뚱한 곳으로 간다. 그리고 아무도 모른다. 못 읽으면 사람이 알아채지만, 잘못 읽으면 모른다.

그래서 우리 규칙 1번은:

못 읽는 것보다 잘못 읽는 것이 나쁘다.

프로그램이 자신 없을 때는 차라리 입을 다물게 만든다.

실제로 있었던 일

프로그램이 없는 바코드를 만들어낸 적이 있다. 676767이라는 숫자를 읽었는데, 그 자리엔 그런 바코드가 없었다.

왜 그랬냐면 — 사진이 너무 작아서, 얇은 줄 여러 개가 뭉쳐서 한 줄처럼 보였다. 그 뭉쳐진 무늬가 우연히 바코드 문법에 맞았던 거다.

비유: 글씨가 번져서 "매"가 "떼"처럼 보이는 것. 둘 다 진짜 글자라서 읽는 사람은 틀린 줄 모른다.

고친 방법: 줄 하나가 점 2개보다 얇으면 "이건 못 믿겠다"고 표시해 두고, 더 나은 답이 나오면 그걸 버린다. 끝까지 이것밖에 없으면 그냥 준다 (없는 것보단 나으니까).

2.6 우리가 제일 자주 틀린 것 — 놀랍게도 시험지

여기가 이 프로젝트에서 제일 재밌는 부분이다.

시험을 보려면 문제지가 필요하다. 우리는 바코드 사진을 컴퓨터로 만들어서 시험 문제로 쓴다. 진짜 사진을 몇십만 장 찍을 순 없으니까.

그런데 문제지가 틀린 적이 여덟 번이다.

예시 1 — 문제지가 바코드를 잘라먹고 있었다

"비스듬히 기울인 바코드"를 만들려고 했는데, 기울이면서 사진 밖으로 삐져나간 부분을 잘라내고 있었다. 바코드 끝이 없어진 거다.

그래놓고 "우리 프로그램은 기울어진 바코드를 못 읽네"라고 결론 냈다. 당연하지, 바코드가 반쪽이었으니까.

예시 2 — 크기를 바꿔도 안 바뀌고 있었다 (이번에 찾음)

"줄 굵기 4점짜리"와 "8점짜리"를 만들어서 비교하려고 했다. 그런데 어떤 바코드는 너무 길어서 사진에 안 들어가니까, 문제지 만드는 프로그램이 말없이 줄여서 둘 다 3.66점으로 만들고 있었다.

즉 똑같은 사진 두 장을 만들어 놓고 "크기를 바꿔서 비교했다"고 하고 있었던 거다.

이게 왜 위험하냐면 — 어떤 바코드는 8점을 제대로 받고, 어떤 건 3.66점밖에 못 받는데, 그 둘의 점수를 나란히 놓고 "이 바코드가 더 약하네"라고 읽게 된다. 실제로는 크기가 다른 걸 비교한 거다.

나는 하마터면 "CODE128이라는 바코드는 흐림에 약하다"고 결론 낼 뻔했다.

고친 방법: 줄여서 맞추지 말고, 사진을 크게 만든다. 그리고 진짜로 몇 점짜리가 나왔는지 사진에 적어 둔다.

예시 3 — 채점 기준이 틀렸다 (이번에 찾음)

바코드를 긁어서 망가뜨린 다음 "읽어봐"라고 하는 시험이 있다.

그런데 채점표가 얼마나 망가졌는지 아예 안 보고 있었다. 90% 지워진 QR코드도 "이건 읽혀야 정상"으로 분류하고 있었다.

그래놓고 나는 보고서에 "QR코드 성적 14.7%"라고 적었다. 마치 프로그램이 못난 것처럼.

실제로는 읽을 수 없는 걸 읽으라고 한 다음 못 읽었다고 감점하고 있었다.

고친 방법:

  1. 망가뜨리기 전후 사진을 빼서 몇 %가 지워졌는지 정확히 잰다
  2. 그 바코드가 얼마나 견딜 수 있는지와 비교한다

QR코드는 종류에 따라 7%~30%까지 지워져도 스스로 복구할 수 있다. 찢어진 부분을 메꾸는 여분 정보를 미리 넣어두기 때문이다.

고치고 나니 QR 성적이 14.7% → 80%가 됐다. 프로그램이 좋아진 게 아니라 채점이 정직해진 거다.

이게 이번 점검에서 제일 중요한 발견이다. 내가 쓴 보고서의 숫자가 틀렸었다.

2.7 실수를 줄이려고 만든 습관

습관 1 — 문턱을 만지기 전에 "켜면 되는지"부터 본다

프로그램에는 "이 정도면 흐린 걸로 친다" 같은 기준선이 여기저기 있다. 뭐가 안 되면 그 기준선을 만지고 싶어진다.

그런데 기준선이 문제가 아닌 경우가 훨씬 많다.

이번에 세 번 그랬다:

만지고 싶었던 것만지기 전에 재본 결과
정지대 검사 기준87건 중 3건만 걸림 → 원인 자체가 딴 데 있었다
확대 기준하나도 안 좋아지고 11배 느려짐 → 되돌림
휘어짐 판정 기준세 값 다 결과가 똑같음 → 여기가 아니었다

세 번 다 만졌으면 느려지기만 하고 아무것도 안 좋아졌을 것이다.

습관 2 — "잘 되는 경우"도 같이 확인한다

"휘어진 바코드를 잘 읽게 고쳤다!" — 좋다. 근데 안 휘어진 바코드는 여전히 잘 읽나?

규칙을 세게 만들면 원래 잘 되던 게 망가지는 경우가 많다. 그래서 규칙마다 "이건 반드시 되어야 한다"는 짝을 만들어 둔다.

예: 상자에 똑같은 라벨이 두 장 붙어 있으면 두 개 다 나와야 한다. "같은 내용이니까 하나로 합치자"는 규칙이 이걸 망가뜨린다.

습관 3 — 숫자에는 항상 단위를 적는다

우리 개발 컴퓨터는 공장 컴퓨터보다 8배 빠르다. 그래서 "50밀리초"라고만 적으면 읽는 사람이 400밀리초를 50으로 오해한다.

실제로 그런 일이 있었다. 검사 프로그램이 개발 컴퓨터 숫자에다 "공장 기준" 이라는 딱지를 붙여 놓고 있었다. 8배 틀린 숫자였다.

2.8 시험은 어떻게 보나

컴퓨터로 바코드 사진을 10만 장 만든다. 종류 14가지 × 상황 21가지를 전부 조합한다.

만들 때 정답을 알고 있으니까, 프로그램이 읽은 걸 정답과 맞춰보면 점수가 나온다.

사진은 저장하지 않는다. 10만 장이면 300기가바이트라서, 만들자마자 바로 채점하고 버린다.

시험 결과 읽는 법

전체 점수는 56.9%다. 근데 이 숫자는 그냥 보면 안 된다.

왜냐면 시험 문제에 일부러 불가능한 문제를 섞어 놨기 때문이다. "어디서부터 안 되는지" 경계를 찾는 게 목적이라서.

나눠서 보면 이렇다:

상황점수
바코드 1개, 깨끗함96.6%
바코드 1개, 읽을 수 있는 조건86.4%
바코드 여러 개 + 문제 5가지 겹침47.7%
바코드 여러 개 + 문제 9가지 겹침25.2%

문제가 겹칠수록 무너진다. 흐림 하나, 어두움 하나는 각각 잘 견디는데 동시에 오면 무너진다.

그리고 재밌는 게 — 시험 본 21가지 상황 중 11가지는 끝까지 안 무너진다. 아무리 세게 해도 읽는다. 무너지는 것들도 대부분 물리적으로 불가능한 지점에서 무너진다.

2.10 한 줄 요약

우리는 바코드 읽는 프로그램을 만들었고, 그 프로그램이 거짓말하지 않게 하는 데 가장 공을 들였고, 놀랍게도 가장 자주 틀린 건 프로그램이 아니라 우리가 만든 시험지였다.
